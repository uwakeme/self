## 1. 执行摘要

### 1.1 问题陈述

人们渴望深度探索自我、理解自己的内心世界，同时也希望用心记录身边每一个重要的人——然而现实中这两个需求长期未被满足：

- **自我认知停留在表面**：我们知道自己的名字、工作、爱好，但很少有人能系统性地梳理自己的性格深层、理想型画像、人生轨迹、愿望清单、身体数据等构成"我是谁"的完整拼图。自我探索缺乏一个结构化的载体。
- **对身边人的了解逐渐模糊**：朋友生日记不住、同事喜好不清楚、与家人的共同经历没有记录。那些本该被珍视的人和事，随着时间流逝变得模糊，关系也因此变浅。
- **碎片化记录无法形成洞察**：备忘录里零散的文字、相册里随手拍的照片、聊天记录中的只言片语——信息散落各处，无法串联成有意义的个人叙事或人物画像。
- **缺少一个私密、专注的自我空间**：社交平台是公开展示的，日记本又不够结构化。用户需要一个既私密又有条理的工具，专属于自己，不求分享，只为看见。

### 1.2 解决方案

「自我档案与人物图鉴」是一款面向个人用户的移动端工具应用，以**温暖手账风格**为设计语言，提供以下核心能力：

1. **自我档案**：结构化记录个人身份、背景、身体数据、喜好、性格分析、理想型、目标愿望、人生轨迹、随想笔记、照片、纪念日等 14 大模块，形成完整的个人画像。
2. **人物图鉴**：为身边重要人物建立详细档案卡片，涵盖基本信息、性格、喜好、互动记录、共同点等，形成人物百科。
3. **关系图谱**：以可视化星形网络图展示用户与各人物之间的关系亲疏与联结。
4. **提醒中心**：基于人物档案中的日期信息（生日、纪念日），自动或手动生成提醒，支持提前天数、重复频率等灵活配置。
5. **隐私优先**：数据本地存储，用户完全掌控自己的信息。

### 1.3 成功指标

| 指标 | 定义 | 目标值（上线后 3 个月） |
|------|------|--------------------------|
| 用户留存率（7 日） | 首次使用后第 7 天仍打开应用的用户比例 | >= 40% |
| 人均档案完整度 | 用户已填写模块数 / 总模块数（14 个自我档案模块） | >= 60% |
| 人均记录人物数 | 每位用户平均建立的人物档案数量 | >= 3 |
| 提醒设置率 | 建立了至少 1 条提醒的用户比例 | >= 50% |
| 周均打开次数 | 用户每周平均打开应用的次数 | >= 3 次 |

## 2. 用户体验与功能

### 2.1 用户画像

**主要用户：阿暖，25 岁，女性，城市白领**

- 重视自我成长和内心世界探索，喜欢做手账、写日记。
- 社交圈中等规模，但希望更深入地了解和维系每段关系。
- 经常忘记朋友和家人的生日，感到内疚。
- 对 MBTI、星座等性格分析工具感兴趣。
- 注重隐私，不愿意将个人信息上传到社交平台。
- 使用习惯：碎片化时间使用，通常在通勤或睡前打开。

**次要用户：小林，22 岁，男性，大学生**

- 刚进入大学，希望系统性地记录和认识新朋友。
- 对自己的性格和未来目标缺乏清晰认知。
- 喜欢收集和整理信息，有轻度"整理控"倾向。

### 2.3 非目标（Non-Goals）

以下功能**不在**本期产品范围内：

- **社交分享**：不支持将个人档案或人物卡片分享至社交平台或生成分享链接。
- **多用户协作**：不支持多人共同编辑同一份档案或人物记录。
- **云端同步**：本期不提供云端数据同步服务，所有数据存储在设备本地。
- **即时通讯**：不具备聊天、消息发送等通讯功能。
- **AI 分析**：不提供基于用户数据的 AI 生成分析或建议（如"根据你的 MBTI 推荐适合的朋友"）。
- **商业化功能**：不包含广告、付费解锁、订阅制等商业化模块。

**目标平台**：iOS + Android 双端支持

**技术栈**：待技术选型后确定。需评估以下方案并选择最优路径：

| 方案 | 优势 | 劣势 | 评估要点 |
|------|------|------|----------|
| Flutter (Dart) | 单代码库双端、高性能渲染、丰富组件生态 | Dart 语言生态相对小、iOS 风格还原需额外调优 | 动画性能、SVG 渲染能力、手账风格 UI 还原度 |
| React Native (TypeScript) | JS 生态成熟、热更新能力、社区庞大 | 复杂动画性能可能不足、原生桥接开销 | 列表滚动性能、动画流畅度、离线存储方案 |
| 原生 (Swift + Kotlin) | 最佳平台体验、完全性能控制 | 双代码库维护成本高、开发周期长 | 团队技术储备、长期维护成本、UI 一致性 |

**选型建议**：
- 如团队无原生开发经验或资源有限 → 优先跨平台方案（Flutter / React Native）
- 如对动画细节和平台原生体验要求极高 → 原生开发
- 本产品涉及大量自定义 UI（手账风格卡片、SVG 关系图谱、底部弹窗动画），选型时需重点评估 UI 还原能力

### 3.5 安全与隐私

| 措施 | 说明 |
|------|------|
| 数据本地存储 | 所有用户数据存储在设备本地，不上传至任何远程服务器 |
| 无强制账号体系 | 不要求用户注册账号或提供手机号/邮箱 |
| 敏感数据保护 | 身体数据、愿望清单等敏感信息存储在设备加密区域（Keychain / Keystore） |
| 最小权限原则 | 仅申请必要的系统权限（通知、相册访问），并在使用时才请求授权 |
| 数据导出与删除 | 提供一键导出（JSON）和一键清除数据功能，用户可随时获取或删除自己的全部数据 |
| 无第三方追踪 | 不集成任何第三方分析 SDK 或广告 SDK |

| 人物图鉴（Tab 3） | P0 | 人物列表、搜索、筛选、添加新人物、人物详情 |

### 4.2 技术风险

| 风险项 | 影响程度 | 可能性 | 缓解策略 |
|--------|----------|--------|----------|
| **本地存储容量限制** | 中 | 中 | 照片采用压缩存储策略（质量 80%，最大尺寸 1080px）；提供存储空间使用情况展示；当存储不足时提醒用户清理 |
| **跨平台 UI 一致性** | 高 | 低 | 严格遵循 Design Token 体系，使用共享的设计组件库；所有页面在 iOS 和 Android 上均需走查验收 |
| **农历日期计算** | 中 | 低 | 使用成熟的农历转换库（如 `lunar-javascript`），覆盖 1900–2100 年范围 |
| **SVG 关系图谱性能** | 中 | 低 | 当人物数量超过 50 时启用虚拟化渲染或 Canvas 替代方案；MVP 阶段人物数量上限设为 100 |
| **本地通知可靠性** | 高 | 中 | 使用系统原生通知 API（APNs / FCM 本地通道），应用启动时重新注册所有未过期的提醒；增加"勿扰模式"检测，在勿扰期间不推送 |
| **数据迁移兼容性** | 中 | 中 | 数据模型采用版本化策略（schema version），升级时自动执行迁移脚本；导出的 JSON 文件包含 schema version 字段 |
